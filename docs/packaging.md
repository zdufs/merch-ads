# Merch Ads — Local `.app` Packaging

Produce a reproducible, locally installable macOS bundle at `dist/Merch Ads.app`
from the `MerchAds` Xcode project, with a stable Launch Services identity, the
existing Dock icon, and local structural + code-signature validation.

Modeled on the Potni nalogi packaging workflow, **adapted for an Xcode project.**
The differences from that SwiftPM plan are the whole point of this doc.

## What changes vs. the SwiftPM (Potni nalogi) version
| Concern | Potni nalogi (SwiftPM) | Merch Ads (Xcode) |
|---|---|---|
| Bundle assembly | hand-built (SwiftPM emits no `.app`) | `xcodebuild` already emits a complete `.app` |
| `Info.plist` | authored `Packaging/Info.plist` | **generated** (`GENERATE_INFOPLIST_FILE=YES` + `INFOPLIST_KEY_*`), merged over a one-key `MerchAds/Info.plist` |
| Icon | `sips`+`iconutil` → `.icns` | `scripts/make_icon.swift` → `MerchAds/AppIcon.icns` (see below) |
| Resource loading | added a `Bundle.module` resolver | Xcode bundles resources natively |
| Bundle ID | minted `si.example.AnotherApp` | **keep** `io.github.zdufs.MerchAds` (settings persistence depends on it) |
| Self-contained? | yes | **yes**, since 2026-08-21 — the bundle carries the engine and its own CPython |

## Goal, and what changed on 2026-08-21
The goal is a **reproducible, validated, stable-identity bundle at a fixed path**.
Since 2026-08-21 it is also a genuinely **standalone** app.

**Code ships inside the bundle. Data stays outside.** `Contents/Resources/engine`
holds the Python modules, `Contents/Resources/python` holds a relocatable CPython 3.12
with `requests`, and `Contents/Resources/run_scheduled.sh` holds the nightly. No system
`python3`, no `pip install`, and no repo checkout is needed to run it — proved with
`env -i`, an empty environment, reading real market data.

What stays outside is DATA: `ads_data*.sqlite`, `.env`, `outputs/`, `KILL`,
`seasonal.json`, `rule_defs/`. They live at the folder named in Settings, passed to the
engine as `MERCHADS_DATA_DIR`. Deleting or replacing the app cannot touch a row.

### The consequence people get wrong

**The app runs the engine INSIDE the bundle, not your checkout.** So an engine-only
Python change does *not* reach the running app until you rebuild:

```bash
bash scripts/package_app.sh --install
pkill -x "Merch Ads"; open "/Applications/Merch Ads.app"
```

Before this was understood, three things agreed on the wrong answer: the tests passed,
the freshness hook only hashed Swift sources, and the standing rule said a relaunch was
enough for Python. A fix could sit in the repo, green, while the app went on running the
old code. `.claude/hooks/app_src_hash.sh` now hashes everything the bundle ships —
`MerchAds/`, `engine/**.py`, `run_scheduled.sh`, `run_stream_drain.sh` — so the Stop
hook blocks on an unpackaged engine change instead of anyone having to remember.

A **DerivedData build ships no engine and no Python**, so it falls back to the Settings
folder and the login-shell `python3`. That is deliberate, and it is why those fallbacks
must keep working.

A fixed `dist/` path also fixes the CLAUDE.md stale-copy gotcha — `open` by bundle
id grabbing an old DerivedData build.

## Architecture
A repo-owned shell script (`scripts/package_app.sh`), not a second build system.
`xcodebuild` is already the source of truth; the script only *packages* its output.
All generated artifacts (`dist/`, the temp derived-data dir) stay out of source and
out of Git.

## Identity & metadata (from the project, not authored here)
bundle id `io.github.zdufs.MerchAds` · display name `Merch Ads` · executable
`Merch Ads` · category `public.app-category.business` · deployment target macOS 26 ·
icon `AppIcon.icns` (`CFBundleIconFile`) · foreground app (no `LSUIElement`/`LSBackgroundOnly`).

## Layout produced
```
dist/Merch Ads.app/Contents/
  Info.plist                 # generated by Xcode
  MacOS/Merch Ads            # Release executable
  Resources/AppIcon.icns     # the app icon
  Resources/engine/          # the Python modules, including rules/
  Resources/python/          # relocatable CPython 3.12 with requests
  Resources/run_scheduled.sh # the nightly job
  Resources/run_stream_drain.sh  # the hourly Marketing Stream pickup
  _CodeSignature/            # ad-hoc signature
```

Code ships inside the bundle; **data stays outside it**. The databases, `.env` and
`outputs/` live in the operator's folder, named by `MERCHADS_DATA_DIR`. That is why
deleting or replacing the app cannot touch a row, and why both launchd jobs can run
`--app` and then depend on nothing but the app and the data folder.

## The icon, and why it is not in the asset catalog
The icon is four black bars rising on a plain white square. `scripts/make_icon.swift`
draws it and packs every size (16 … 512@2x) into `MerchAds/AppIcon.icns`:

```
swift scripts/make_icon.swift MerchAds
```

It ships as a **legacy `.icns`** — `CFBundleIconFile`, no asset catalog. An
asset-catalog `AppIcon` makes Xcode set `CFBundleIconName`, and macOS 26 then draws
the icon on its light system "platter". Around a white icon that platter reads as a
grey rim, with the white square's corners visible inside it. The `.icns` path is
rendered flat, so the tile is just white with black bars and macOS rounds the
corners itself. Two things follow:

- The one-key `MerchAds/Info.plist` exists only to carry `CFBundleIconFile`;
  Xcode ignores `INFOPLIST_KEY_CFBundleIconFile`. It is excluded from Copy Bundle
  Resources by a synchronized-group exception in the project file.
- `package_app.sh` **fails the build if `CFBundleIconName` comes back**, so the rim
  cannot return unnoticed.

After changing the icon, the Dock keeps showing the old pinned tile until its cache
is cleared:

```
mv "$(getconf DARWIN_USER_CACHE_DIR)com.apple.dock.iconcache" /tmp/ && killall Dock
```

## Script steps (`scripts/package_app.sh`)
1. Resolve repo root from the script's own location; `set -euo pipefail`.
2. Preflight: require `xcodebuild`/`codesign`/`plutil` and the `.xcodeproj`.
3. Clean only its own outputs (`dist/Merch Ads.app`, the temp derived dir).
4. **Release** build to `${TMPDIR}/merchads-package-derived` — a repo-local
   derived path gives SQLite `disk I/O error` on `build.db` (the dedicated-scratch
   fix; same class the Potni plan called out).
5. Locate the built `*.app`; `cp -R` to `dist/`.
6. Ad-hoc re-sign (`codesign --force --sign -`) for a clean signature after copy.
7. Validate (below); register with Launch Services; print the path + `open` command.
8. Any missing tool / product / plist key aborts non-zero — never a partial app.

## Signing & Gatekeeper
Ad-hoc signing gives a consistent signature and catches malformed nested code. It
does **not** establish a Developer ID, so Gatekeeper may still refuse the app — that
is expected and is not the success criterion for this local-only workflow.

## Verification (all pass)
- script exits 0; `plutil -lint` accepts `Info.plist`;
- `CFBundleIdentifier == io.github.zdufs.MerchAds`; `CFBundleIconFile` present and
  `CFBundleIconName` absent (the macOS 26 platter guard);
- executable + `Resources/AppIcon.icns` exist; `codesign --verify --deep --strict` valid;
- copied outside the repo it still launches and renders live data;
- Launch Services reports the stable id + foreground type; Dock shows the icon;
- all 15 sidebar destinations present.

## Non-goals
Developer ID signing · notarization/stapling · DMG/PKG · auto-update · App Store ·
universal-vs-arm pinning · bundling the Python engine or DBs · version automation.

## Usage
```bash
./scripts/package_app.sh            # build + validate → dist/Merch Ads.app
./scripts/package_app.sh --install  # same, then copy to /Applications (re-signed,
                                    #   registered with Launch Services)
open "dist/Merch Ads.app"
```
`--install` replaces any existing `/Applications/Merch Ads.app` with the fresh
build; it's reversible (just delete it). Same bundle id as `dist/`, so UserDefaults
settings are shared.
Development is unchanged: `xcodebuild … -scheme MerchAds … build` (Debug) and the
`-rehearsal` launch argument for the no-write rehearsal mode.
