# Full review — MerchAds, 2026-08-04

A complete review of the engine and the Mac app: what the features are, which
ones earn their place, which ones don't, and what to build next. Written
2026-08-04. Part 3 records what was actually done about it on 2026-08-05.

Everything here was checked against the live account, not read off the code.
Line references are as of 2026-08-04 — many have moved since the fixes landed.

## How the review was produced

- Three read-only audit agents ran in parallel: one on the Python engine, one
  on the SwiftUI app, one on the rules DSL package.
- Over thirty `appctl.py` read endpoints were called for real, across markets,
  and timed.
- The rules DSL was exercised end to end: validate, preview, save, delete.
  A preview ran against all 43,597 US targets.
- The merchdash.net docs were fetched, and every feature borrowed from them
  was tested against real data.
- Four app screens were captured from the running app and judged against
  Apple's Human Interface Guidelines.
- The engine test suite was run (145 tests at that point).

# Part 1 — The review

## Verdict

The product is good and the numbers are trustworthy. Every figure shown in the
app matched the engine exactly. All thirty-plus read endpoints worked.

The problem was underneath. The nightly pull had been failing with disk I/O
errors almost every night since late June. Nothing told anyone. And the newest
features — the rules apply path, the export-snapshot preservation — had real
safety gaps.

## 1. The pipeline was silently degrading

`phase0_pull` hit `sqlite3.OperationalError: disk I/O error` **89 times since
2026-06-24**. Nearly every night. The rate was increasing. On the morning of
the review it killed the US targeting-report store.

The visible consequence: UK and DE perf tables were stuck three days behind,
and DE had five report jobs pending.

**There was no way to notice.** Four separate things had to be wrong at once,
and all four were:

- `run_scheduled.sh` checked no exit codes. Every phase ran regardless.
- Discord was the only failure channel, and it was off by the `NO_DISCORD` file.
- `health` judged freshness from `campaign_perf` alone. That table stayed green
  while `targeting_perf` and `search_term_perf` drifted days behind — which is
  precisely the failure mode that had already frozen US bids twice.
- `alerts` returned "no alerts" exactly when data was missing, because every
  alert branch needs a snapshot date to compute against.

Two more engine-wide problems in the same family:

- **`export_snapshot.py` was dead code.** The commit that added it said it
  preserves per-ASIN economics before a 2 GB catalogue export is deleted.
  Neither deletion site ever called it. The `asin_econ_snapshot` table was
  permanently empty. The feature had shipped in name only.
- **HTTP 207 was treated as success in about ten modules.** Amazon returns 207
  even when every item in a batch failed. The code then mirrored local state on
  top of that, so the local database could quietly disagree with Amazon.

## 2. The merchdash-inspired features, tested

Each of these was borrowed from merchdash.net. Each was exercised against the
live US account.

| Feature | Verdict |
|---|---|
| Rules DSL + editor | **Works, impressive core.** Rolling windows correctly rejected with an honest explanation of why. A preview evaluated 43,597 targets in 1.1 s with per-condition traces and per-design break-even resolved. The *apply* path had holes — see below. |
| AI Copilot | Built, unconfigured. Needed `ANTHROPIC_API_KEY`. Failed gracefully with that exact message. |
| Watchlist | Works. Empty — nothing pinned. |
| Accumulated ASINs / Keywords | Work. Real cross-campaign rollups, fast. |
| Reports (custom timeframe) | Works. The July rollup matched `periods` previous-month to the cent. |
| Change history & rollback | Works. Audit plus undo, with `snap=` provenance. `undo` itself had zero tests. |
| Preview & debug traces | Work everywhere — rules, approval queue, kill list. |
| Sync calendar | Works. One of the best screens in the app. |
| Cross-purchase | Wired, waiting for its first purchased-product snapshot from the nightly. |

The rules DSL gaps that mattered, all in the apply path:

1. `rules/executor.py` **never checked Amazon's response.** Every write was
   logged `submitted` and counted as applied, even on a rejection. This ran
   nightly.
2. **No snapshot-freshness gate.** The hardcoded phases fail closed on stale
   data. A DSL rule would happily pause targets off week-old evidence.
3. The econ gate only inspected the `IF` condition. `LET x = break_even * 0.9`
   followed by `setBid(x)` slipped past as non-economic.
4. `keyword.bid` was actually the **ad-group default bid**. No per-target bid
   existed in the schema. So `setBid(bid * 0.85)` computed from the wrong base
   and could *raise* an under-bid keyword.
5. The app's own shipped rule templates crashed the whole preview when
   `default_bid` was NULL, because `MIN`/`MAX` used Python builtins that can't
   take `None`.
6. `IN LIFETIME` parsed but was ignored — identical to `CURRENT`.
7. Validation accepted unknown verbs and unknown fields. `keyword.paws()`
   validated fine; you found out at apply time.

## 3. What's useful, what isn't

**Earning their place**, verified working with real data behind them: the
Dashboard period stack, Profit (royalty-aware, matching the engine to the
cent, honest about not counting organic halo), the Approval Queue with its
"heads-up: the nightly still auto-applies this plan" banner, the Kill List
with economics transitions, Harvest, Seasonal (15,674 tags), organic halo,
CSV intake (2M-row export scanned in 19 s, 1,482 new designs routed), All
Markets (never mixes currencies — genuinely good data honesty), audit and
undo, and the ⌘K palette.

**Built but idle** — these needed an adopt-or-cut decision:

- Rules: zero rules authored. Watchlist: zero pins. Copilot: no key. Three
  flagship features at zero adoption.
- KDP: fully scaffolded, not live. No profile ID, no books, and **no UI** —
  book royalties could only be entered from the command line.
- `nudges` was buried under System Health → Advisor. There were 43 pricing
  nudges pending that you could not find from the sidebar.
  (Superseded 2026-08-14: the operator asked to drop this feature. The Advisor
  section, the dashboard playbook-nudge pill, and `AdvisorView` are all removed.
  The `nudges` engine endpoint still exists; nothing in the app reads it now.)
- Dead weight: `command_poll.py` and its never-loaded launchd job, the `status`
  bridge path no view called, a `backfill-daily` timeout tier for a button that
  didn't exist, about ten orphan root scripts, 13 MB of stale caches.

**What didn't make sense as presented:**

- **All-time and previous-year profit.** The dashboard showed "Estimated profit
  4,951 US$" beside all-time spend of 93,853 US$. The profit covered only the
  ~125 banked days while spend included imported console history. The "125
  days" caption under all-time numbers made it worse.
- **Two YTD definitions.** `periods` YTD included imported history (14,409);
  `overview` and `monthly` did not (6,243). Not user-visible then, but a
  landmine.
- `history_import.py` filled the table `periods` reads, but nothing could
  invoke it. The app displayed history it had no supported way to produce.
- Mysterious "CATCH-UP (read-only)" runs appeared in the log from a script that
  wasn't in the repo.

## 4. App quality — UI, speed, safety

The design had come a long way: consistent cards, honest captions, numbers
matching the engine everywhere compared.

**Speed**, all fixable in an afternoon:

1. The dashboard's eight "parallel" fetches serialised through a single serve
   worker pipe. A market switch cost the *sum* of the reads, and `health` was
   fetched twice.
2. Nine pure database reads were missing from `fastCommands`, so each paid a
   fresh ~300–600 ms interpreter start. `campaigndaily` refired on every
   campaign-scope click.
3. The first bridge call resolved `python3` through a **login shell,
   synchronously, on the main thread** — the classic first-click freeze.
4. `bidreport` took 4 seconds.

**Action safety.** The `ActionCoordinator` design was genuinely correct: KILL
re-checked server-side, market captured at intent creation, preview receipts
bound by ID. Two bypasses undermined it. `RulesApprovalQueue` called the bridge
directly, so no KILL-disabled button and no "always confirm". And **rehearsal
mode permitted `maxbid --set`** — a real bid-ceiling write. Meanwhile rehearsal
*blocked* a dozen pure reads, which killed the Rules workflow in exactly the
mode meant for practising it.

**Polish.** Ghost skeleton rows padded the Approval Queue. The Rules screen
cold-started as a blank editor. Forced light mode and a fixed hex palette
contradicted DESIGN.md's "semantic, dark-first". Fourteen `GlassEffectContainer`
wrappers had no `glassEffect` children — inert scaffolding. The sidebar and page
headers used frozen point sizes, ignoring Dynamic Type. `Format.percent`
hard-coded a decimal point next to fully-localised money, so a German locale
rendered `1.234,00 €` beside `18.2%`.

**Concurrency.** The project targeted macOS 26 but compiled in Swift 5 mode, so
none of the `@MainActor` and `Sendable` discipline the code was written to was
actually enforced. There was one real data race in the bridge watchdog.

**Docs.** `claude-code-handoff.md` called itself the current contract but was
missing 15–19 shipped commands, including live-write surfaces and the global
`maxbid` safety ceiling.

## 5. What to build next

Ranked as of the review:

1. **Pipeline health, before any feature.** Everything else is only as good as
   last night's pull.
2. **Wire what's already built**: export_snapshot, a history-import entry
   point, the backfill button, a KDP book editor, the copilot key.
3. **Rules hardening to unlock auto mode**: check API responses, snapshot gate,
   econ gate on args and LETs, None-safe functions, semantic validation.
4. **Store per-target bids.** Fixes `setBid` semantics, makes `resetbids`
   cheaper, enables a real bid-versus-performance chart.
5. **Budget ceiling.** `setBudget` had no clamp at all.
6. **Bank per-target daily deltas going forward.** Rolling windows and
   trend-brake rules are impossible without per-entity daily history. This is
   the one real moat extension and it remains unstarted.

   **Correction, 2026-08-06.** This item originally said "snapshot diffs would
   unlock them in about 90 days". That was wrong on both halves and the wrong
   idea should not be picked up again. The perf snapshots are ROLLING
   trailing-30 windows, not running totals. Subtracting one snapshot from the
   one before it gives you the day that entered the window minus the day that
   left it 30 days earlier — not a day. There was no arithmetic that could
   recover a per-day figure from them. And the wait was unnecessary: Amazon
   serves a DAILY-grouped targeting report over its ~92-day retention, so the
   history could simply be asked for. See the shipped section below.

**Not worth building**: dayparting (no hourly data at this API tier), folder
watching (drag-drop was the right call), a visual rule builder (the text DSL
plus templates covers it).

# Part 2 — The three deep audits

## Engine (Python)

86 `appctl.py` subcommands, cleanly wired — parser keys and dispatch keys
matched exactly, no orphans either way. Fifteen were entirely absent from the
handoff contract, including live-write surfaces (`pause-target`,
`enable-target`, `setbudget`) and `maxbid`, the global bid ceiling that clamps
every write.

**The nightly pipeline** ran twenty-one steps per market with no `set -e` and
no exit-code check anywhere. A crashed `phase0_pull` was followed immediately
by `phase2_apply --apply --auto` and `phase3_bids --apply --auto` against live
accounts. This was confirmed in production, not theorised.

**Test coverage** was 21 files and about 145 cases, all fixture-based. The gap
was stark: **zero tests imported any `--apply --auto` stage except `phase2`**,
and even that only through one helper. Every `appctl` write command was
untested, including `undo` — 74 lines of regex-driven state restoration that is
the rollback of last resort. `ads_client.py`, which performs every Amazon
mutation, was touched by exactly one test.

**Quality hotspots**: `appctl.py` was 3,608 lines, 22% of the Python codebase
in one file. `confirm()` was reimplemented eleven times. The CVR floor appeared
in three files; `MIN_BID`/`MAX_BID` disagreed across modules. There were 19
broad `except` clauses.

**The data layer was the strong part.** `latest_snapshot`, `snapshot_age_days`
and a fail-closed `snapshot_gate` were properly codified, with a structural
lint that pairs "filters table T by date" against "reads a date from T" across
the whole engine, plus a test that guards the guard. Two exemptions weakened
it, and one of them was `appctl.py` — the largest file, with about thirty dated
queries, in exactly the place regressions had happened before.

Top five, ranked: the rules executor ignoring API responses; 207-as-success in
ten modules; no exit codes in the nightly; `cmd_health` reading the wrong
table; `export_snapshot.py` never being called.

## Mac app (SwiftUI)

26 screens, every one reachable, no orphan enum case. State management was
modern and consistent: `@Observable` with `@MainActor` throughout, zero
`ObservableObject` anywhere.

`PythonWorkerPool` was well designed — an actor per market, single FIFO drain
loop, poison-on-failure. The problem was that the allow-list left nine pure
reads off it, and that a single pipe serialises a screen's fan-out.

Error surfacing had a good central choke point: every `BridgeError` landed in
the Errors tab even when a caller swallowed it with `try?`. The leaks were
specific — a nil econ-gate read was indistinguishable from "gate open", the
rules queue rendered a bridge failure as "nothing pending", and
`ActionCoordinatorError.killActive` never reached the issue centre at all.

Dead or misfiled: `PlaybookView.swift` declares `AdvisorView`; the `status`
bridge path had no caller; the `backfill-daily` timeout tier had no button.
(Superseded 2026-08-14: `PlaybookView.swift`/`AdvisorView` deleted — the
operator dropped the playbook-nudge surface.)

Gaps against the product spec: Settings was missing every per-market economics
and strategy knob the spec asked for, KDP had no UI, there was no PDF export
and no daily trend chart. Roughly a third of the app post-dated both spec
documents.

## Rules DSL

The grammar the parser actually accepts was mapped from the lexer and parser
rather than the docs, and the two disagreed in both directions.

Docs promised things the parser or executor rejects: `.setState(…)`,
`.createKeyword(…)` and `.setBiddingStrategy(…)` parse and preview fine, then
fail at apply time. Relations via dot (`keyword.campaign`) do not work — the
row is a flat dictionary. `IN LIFETIME` is read by nothing.

The parser accepts things the docs never mention: `WHEN` as an `IF` synonym,
`IS`/`IS NOT`, `NOT CONTAINS`, four extra functions — and, more seriously,
**any verb name at all** and **any action target**, with the written target
silently discarded in favour of the loop entity.

Safety gates were traced one by one. KILL fires, twice over. The change cap
fires. The max-bid clamp fires for bids and does not exist for budgets. The
econ gate fires, but only against the `IF` condition. Snapshot freshness was
not checked at all.

Correctness risks worth recording: malformed numeric literals crash out of
`validate` with a raw `ValueError` in a shape the editor cannot display;
`MIN`/`MAX` break the fail-closed `None` semantics the rest of the evaluator
maintains; the approval store's change id excluded the arguments, so approving
what you saw could apply a different value; rule files collide when two display
names slug identically.

**One audit claim was wrong.** The report said `docs/rules-dsl.md` — the
authoring guide — does not exist. It does: 124 lines, committed 2026-08-01 as
`1048c9d`. Recorded here so the error doesn't propagate. What the DSL genuinely
lacks is an in-app field reference, not a document.

# Part 3 — What was done about it

Remediated 2026-08-04 and 2026-08-05 on `fix/stale-perf-snapshots`, in twelve
blocks, test-first throughout. The engine suite went from 145 tests to 192 and
the Swift suite to 68. All green. The app was rebuilt and reinstalled to
`/Applications` after every block.

## 1. Pipeline health — `47b92b1`

Every phase in `run_scheduled.sh` now runs through a `step()` wrapper that
records a non-zero exit. The loop still continues past a crash on purpose — one
market's failure must not strand the other five — but the failure is no longer
invisible. The run writes `outputs/last_run_status.json`, and the closing macOS
notification says `RUN FAILED` with the failed steps instead of the usual
digest.

A `data_stale` alert kind was added. It fires when a perf table's newest
snapshot is four or more days old. That is deliberately the same threshold at
which `db.snapshot_gate` freezes writes — one threshold everywhere. Three days
was rejected: EU markets sit at a structural two-day Amazon lag, so a
three-day alarm would fire every morning for all six markets, which had already
happened once before.

`health` stopped lying. `latest_data` is now the worst of the three perf
tables, with per-table dates and a `stale_tables` list, plus the last run's
status. `export_snapshot.py` gained an `--auto` mode and is wired into the
nightly before the catalogue export is pruned, so the feature that had shipped
in name only now actually runs. Write-failure diagnostics name the database the
connection really uses, rather than a module-level path that was wrong whenever
the shared connection was in play.

`tests/pipeline_health_tests.py` pins the alert threshold and the worst-table
rule, including the case that must stay silent.

## 2. Rules DSL hardening — `6abfc7f`

Seven gaps, each pinned by a failing test first.

The executor now checks every Amazon response. A rejected write is reported
`failed`, logged `result=failed`, and is not counted as applied. It also gates
each change on snapshot freshness, using the same perf table the rule read, so
the DSL fails closed on stale evidence exactly like the hardcoded phases.
Successful pauses and enables mirror local state.

The econ gate now sees economics that reach a write through a `LET` binding or
through the action's arguments, not only through the `IF` condition.

`MIN`, `MAX`, `CLAMP`, `ROUND`, `FLOOR`, `CEIL` and `ABS` propagate `NONE`
instead of raising, and an action with a `NONE` argument is skipped. This
mattered immediately: the app's own shipped templates crashed the entire
preview on any NULL default bid. One bad row now records an error and the
preview continues.

`IN LIFETIME` resolves snapshot metrics to `NONE`, so it means something
honest rather than silently equalling `CURRENT`. Validation gained a semantic
pass that rejects unknown fields and unknown or not-yet-executable verbs with
line numbers. Approval-queue change ids now hash the arguments, so approving
what you saw cannot apply a different value.

Verified against the live US database: a template preview over 43,597 targets
produced 46 matches with no errors.

## 3. App speed and rehearsal honesty — `9192ab1`

Nine pure database reads moved onto the persistent serve worker: `alltargets`,
`campaigndaily`, `report`, `harvest-prune`, `negatives-preview`, `seasons`,
`seasonal-preview`, `econ-gate` and `sales-report`. Each had been paying a
fresh interpreter start of roughly 300–600 ms. `campaigndaily` fired on every
campaign-scope click.

The worker pool now runs up to three serve processes per market and picks the
least loaded. A single pipe is strictly FIFO, so the Dashboard's seven-call
fan-out used to cost the sum of its reads. The Dashboard also reuses the health
response `AppState` already fetched, instead of scanning every market database
a second time.

The `python3` login-shell lookup is warmed off the main thread at launch. It
used to run `zsh -lc` with `waitUntilExit` inside the first `@MainActor` bridge
call, which was the first-click freeze. Chart hover stores the hovered date and
scans pre-parsed dates, rather than parsing 2n dates per mouse move at 60 Hz.

Two rehearsal holes closed. `maxbid --set` and `sales-report --import` are now
recognised as write forms, so rehearsal denies them and the fast bridge never
routes them to the worker; rehearsal could previously write the real bid
ceiling. In the other direction, rehearsal now allows the read-only workflows
it had been blocking, including the entire Rules preview and validate path.

## 4. Action safety — `99f7762`

`rules-approve` goes through `ActionCoordinator` like every other Amazon write,
which gives it the server-side KILL re-check, the market captured at intent
creation, rehearsal receipts and audit visibility. The Apply button is disabled
under KILL with a reason. A failed queue load now says so instead of rendering
as "no rules pending".

Swallowed errors were surfaced. An unreadable econ gate is a warning rather
than silence that reads as "gate open". Failed re-pulls name the markets that
failed, and a KILL switched on mid-run is no longer discarded. A failed trend
load says "Trend unavailable" instead of looking like an empty chart. Four
views that folded a blocked action into the ready path now show the KILL
message immediately rather than making a doomed round trip.

Two market-switch bugs fixed: the Import screen reloads on a market change
instead of showing the previous market's coverage, and the Actions screen
re-keys so its reset-bids preview refreshes after a nightly run.

## 5. Per-target bids — `e79822a`

The engine had no per-target bid anywhere. A new `targets` mirror table is
banked by the nightly pull from `/sp/targets/list` and `/sp/keywords/list`,
replaced atomically with the same retry discipline as the other bulk writes.

Measured on the live US account: 419,250 targeting clauses and 5,057 keywords,
fetched in about nine minutes, stored in two seconds, 424,307 rows of which
319,685 carry their own bid.

The DSL, `alltargets` and the app's new Bid column all read it, with an honest
`bid_inherited` fallback when a clause has no bid of its own. After the first
bank, all 43,486 traffic-bearing US targets carried their real bid instead of
their ad group's default.

## 6. Idle features wired — `0265827`

`history_import.py` finally has a CLI entry point, so the table that the
dashboard's period stack reads can actually be filled. The Import screen routes
a dropped CSV to it automatically when the file is not a Merch sales report.

The Actions screen gained the backfill button that the bridge already had a
timeout tier for. Settings gained a KDP books section over `appctl kdp-book`,
so book royalties no longer require the command line — a book with no entry
fails closed, and until now there was no in-app way to fix that.

## 7. UI polish — `d3f3b86`, `7ac70f6`

The Dynamic Type migration was finished. The sidebar, page headers and the
stragglers in five other views now use the relative typography tokens that
`Typography.swift` had already defined, with two new tokens for the page
heading and subtitle.

`Format.percent` is locale-aware like `Format.money` two functions above it. A
German-locale card had been rendering `1.234,00 US$` next to a hardcoded
`18.2%`. User-typed filters use the matcher users actually expect,
diacritic- and case-insensitive.

The fourteen inert `GlassEffectContainer` wrappers were removed, with zero
visual change, and DESIGN.md carries a dated addendum naming the flat card
treatment the design of record. Approval Queue tables size to their rows
instead of painting a page of empty stripes under four real rows. The Dashboard
watch row shows pending playbook nudges — 46 of them had been sitting unseen
under System Health. (Superseded 2026-08-14: the playbook-nudge pill was
removed at the operator's request, along with the whole Advisor section.)

## 8. Swift 6 mode and the copilot — `fa1c0a9`, `dda3417`, `00408dd`

The project targeted macOS 26 while compiling in Swift 5 mode, so the
concurrency conventions the code was written to were never checked. Turning on
Swift 6 surfaced exactly three things. The bridge watchdog flag was a real data
race, written by a timer queue and read by a worker thread with no ordering; it
is now a proper lock. The rule-syntax font and highlighter touch AppKit state
and are now main-actor isolated, as is their test class.

The AI copilot was removed rather than configured, by operator decision. The
Swift half went in `fa1c0a9`; the engine half, about 100 lines, in `dda3417`.
Forced light appearance was recorded in DESIGN.md as deliberate rather than
debt. (Superseded 2026-08-14: the operator asked for dark mode. Every Theme
color now carries a light and a dark hex, a Settings picker selects System /
Light / Dark, and the app no longer forces light. Light mode is unchanged.)

## 9. Engine truthfulness — `88bcd07`

Amazon answers 207 even when every item in a batch errored. Every write's batch
result now parses the v3 success and error arrays into a failure count and the
exact rejected ids, because the client owns the mapping from batch position to
id. `_http_ok` and the rules executor both require zero item failures on top of
the status check. Phase 2 pauses and rollbacks, phase 3 bids and the seasonal
scheduler mirror local state only for items Amazon accepted, and log the
rejected ones as failed.

Budgets got a ceiling. Bids had one; budgets had nothing between a mistyped
rule and a very expensive campaign. `maxbid --budget` stores it, the campaign
budget writer clamps through the same path as bids with the same "adjusted"
audit trail, and Settings gained a third field.

Applied bids now write through to the targets mirror, so the DSL and the app's
Bid column stay honest between nightly pulls instead of going stale until
10:00. And `phase0_pull` exits non-zero when structure parts or report stores
genuinely failed, so the new step tracker hears about the "printed FAILED, exit
0" class. Deferred reports stay normal, because they are.

## 10. Report recovery — `8a2b113`

This was the actual cause of UK and DE sitting days behind. A report that
outran the 25-minute poll window was deferred, and the next run requested a
fresh window — abandoning the old job even when Amazon completed it minutes
after we hung up. Amazon kept finishing reports nobody downloaded.

Each pull now checks leftover jobs before requesting new ones, and banks any
that completed, under their own window date. Jobs undownloaded past 48 hours
are marked expired, since the download URLs stop working anyway. Health's
pending counter ignores dead jobs, which removes the phantom "pending" reports
DE had been showing.

UK and DE were then healed by hand the same day: both went to fresh data, no
stale tables, no pending reports.

## 11. Housekeeping — `ca14afa`

An `attic/` folder with a README now holds the retired scripts: the Discord
status poller and its never-loaded launchd job, plus four one-off debug and
smoke-check scripts. Nothing was deleted, so anything can be moved back.

Thirty-eight stale one-shot artefacts left `outputs/`, moved to a scratch
directory rather than removed. The intake caches stayed, because
`import-preview` genuinely reads them. The run log rotates at 10 MB.

The mystery was solved: the CATCH-UP entries were ad-hoc one-off runs. Crontab
and LaunchAgents are clean, so no hidden automation exists. And the last
seventeen undocumented commands were written into the handoff, so the document
that calls itself the current contract is one again.

## 12. Small polish — `97962ef`

`bidreport` went from 3,989 ms to 73 ms. The enrichment step had been running
`SELECT DISTINCT` across the full targeting history — roughly 1.7 million rows
— to label a few dozen changes. It now looks up only the changed target ids,
against the mirror first and the latest snapshot as fallback.

The audit trail pages. The engine takes a `--before` cursor and reports whether
more exists; the app shows "Load older writes" instead of stopping dead at 500
rows. The detail pane became its own view, so the toolbar's loading spinner no
longer re-evaluates all 26 screens. The all-markets ASIN search names the
markets that did not answer, instead of quietly omitting them.

One item was closed as reviewed-no-change: the command palette opening SQLite
per keystroke. The cost is the unindexable `LIKE` scan rather than the open, a
shared connection would race across the detached query tasks, and the 180 ms
debounce already bounds the rate.

## The process guard — `e7d412f`

`.claude/hooks/engine_edit_guard.sh` blocks edits to engine `.py` files while

## Item 6 shipped — per-target daily banking, 2026-08-06

The last open item from section 5 is done. It is no longer parked.

What was built, in order: a `target_daily` table; a `backfill_target_daily.py`
that asks Amazon for DAILY-grouped targeting reports over its retention window;
a fifth nightly report (`targeting_daily`) in phase 0 so the table keeps
filling; rolling `IN LAST N DAYS` windows in the rules language; a
`db.daily_window_gate` so a rule with a hole in its window refuses to write;
`basis` / `days_banked` / `first` / `last` on the `history` endpoint; and the
app changes that draw the per-day series and say what it is.

Banked at the end of the backfill:

| Market | Days | Rows | From |
|---|---|---|---|
| US | 92 | 727,777 | 2026-05-06 |
| ES | 43 | 129,117 | 2026-06-24 |
| IT | 43 | 99,101 | 2026-06-24 |
| FR | 43 | 54,418 | 2026-06-24 |
| DE | 43 | 37,968 | 2026-06-24 |
| UK | 43 | 24,252 | 2026-06-24 |

The EU markets are not partially seeded. They genuinely have 43 days because
EU ad activity began 2026-06-24, and `campaign_daily` agrees independently. A
market with a short honest span is healthy, and nothing in the UI treats it as
a warning.

Two things about the window are deliberate. It ends two days before today,
because the freshest day or two is still under-attributed and would read as a
collapse in sales. N is capped at 92 days, which is Amazon's reporting
retention — asking for more is an error, not a silent short answer.

The app half is small but it is the point of the whole item. A trailing-30
snapshot series and a true per-day series look identical on a chart and mean
completely different things, so every drill-down chart now carries a caption
built from `basis`, plus how many days are banked and which dates they span.
System Health gained a "Per-day history" column per market, reading
"not banked yet" where there is none — that column is where the operator finds
out why a rolling-window rule went quiet.
